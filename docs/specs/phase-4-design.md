# Phase 4 design: Learner and skills

> Source of truth for Phase 4 (`docs/ROADMAP.md`: "Finished tasks become reusable skills, promoted only with evidence. Gate: bad skill rejected; skill replays a past task"). It builds on Layer 1 (`docs/specs/layer-1-design.md`, `docs/specs/bootstrap-conductor.md` R1-R63, E1-E5) and on Phase 2 (`docs/specs/phase-2-design.md`: the Auditor's `audit` events and the per-role scores) and must not contradict them or `docs/DECISIONS.md`. Plan tasks: `docs/specs/phase-4-queue.json`. New decisions this design needs are listed at the end as **proposed** entries (D-055 to D-059); they are not in `DECISIONS.md` yet.
>
> The numbered sections below use the coverage-map format (`core/coverage.py`): each top-level list item in a `## N.` section is requirement `N.k`. "Why", "Builds on", "Needs Ben" and "Risks" are unnumbered on purpose.
>
> Terms: a **trace** is the plain-code summary of one finished task, rebuilt from the ledger. A **win** is a task with a ledger `pass`. An **audited win** is a win that the Phase 2 Auditor re-checked without a confirmed defect. A **skill** is a short, versioned instruction pack (advice for one role) that is injected into that role's prompts. A **replay** re-does a past task in a scratch worktree, with or without a skill, and plain code runs the task's original tests. Phase 4 builds **guidance skills** only; deterministic venture runbooks and canaries belong to Phase 6.

## Why (PURPOSE trace)

- **"Anything done once can be repeated without re-figuring it out"** (PURPOSE, success). Today every task starts from nothing; the same dead ends, wrong turns and conventions are paid for again. The Learner keeps what worked.
- **False claims and bare-minimum work** (PURPOSE failures). A lesson drawn from one lucky run, or from a noisy one, would teach bad habits. So a skill is promoted only by plain-code evidence: at least two independent audited wins, a clean static scan, and a replay that passes the original tests and is no worse than the same replay without the skill. No AI votes on promotion.
- **Forgetting progress.** Dead ends and fixes are already files (`state/dead_ends.jsonl`, trouble notes) and ledger events. The Learner turns them into something later agents are actually given.
- **The tuning promise.** D-026: "the Learner tunes them later, with Ben's approval"; Phase 2 (D-041): scores are shown only until the Learner acts on them with evidence. Phase 4 delivers tuning proposals, never silent changes.

## Builds on (do not rebuild)

- **The ledger and run reports** (`core/ledger.py`: `pass` with merge evidence `task_commit`, `final_sha`, `merges`; `run_report` payloads including `claim`, `easy_out`; `fail` events with `note: "false_claim"`; Phase 2A adds `audit` events with `verdict`, `findings`, `confirmed`, `unconfirmed`; Phase 2B adds `challenge`). All traces derive from these (D-001).
- **Dead ends and easy-outs** (`state/dead_ends.jsonl`, shown to later agents as `KNOWN DEAD ENDS:`; `state/easy_outs.jsonl`). Phase 2B marks a challenged dead end with `"challenged": <run_id>`.
- **Role plumbing** (`core/roles.py` `ROLE_NAMES`/`DEFAULTS`/`role_text`; `Team`/`real_team`; `SMOKE_ROLES`; `Conductor._call` with metering, caps, holds, stops, tamper guard R9/R14/R42; per-task worktrees `core/worktrees.py`; the merge journal `core/finalize.py`; judges that run a task's `test_cmd` without a shell, R1).
- **Prompt construction** for Builder, Test writer, Troubleshooter and Planner in `core/bootstrap.py` (headings such as `REVIEW FEEDBACK:` and `KNOWN DEAD ENDS:`), where `SKILLS` is added.
- **Ben's channel and status page** (`core/channel.py` digest and kinds, `queue.jsonl`, answers; `core/status_page.py`).
- **Phase 2C scores** (`core/scores.py`, `state/scores.json`) for tuning proposals only (P4E).
- **Per-day usage caps** (D-020, `core/usage.py`): Learner and replay runs are ordinary metered Claude runs and slow down, never swap engines, when capped.

## 1. Traces

- **`core/traces.py` `build_trace(ledger, state_dir, repo, cid) -> dict` derives a trace from ledger events and the state files they point to, nothing else.** Rebuilding from the same ledger gives an identical trace (same JSON bytes). Traces are cached in `state/traces/<cid>.json`; a missing or corrupt cache is rebuilt.
- **Trace fields.** `cid`, `title`, `section` (capped), `spec_ref`, `task_kind`, `files_in_scope`, `test_files`, `test_cmd`, `status`, `attempts`, `tokens_used`, `false_claims` (count), `easy_outs` (list of reasons), `dead_ends` (list of capped notes, with `challenged` flag), `review_reasons` (capped list), `judge_evidence` (test result, mutation score), `audit` (`clean` | `findings` | `none`, `confirmed` count), `error_signatures` (normalized first lines of failing test output and blocker errors: paths, numbers, hashes and addresses replaced by placeholders), `replay_anchor`, `replayable` (bool).
- **Scrubbed.** Every free-text field passes `traces.scrub`: token-like strings (long hex or base64 runs, `sk-`, `ghp_`, bearer headers, 16-digit runs) and anything resolved by `core/secrets.py` redaction (when Phase 3 is merged) are replaced; each field is capped. A planted secret in a source note never appears in a trace.
- **Replay anchor.** `replay_anchor = {"base", "tests_commit", "task_commit", "final_sha"}`: `base` is the layer tip the task's tests commit was made on (as Phase 2 section 3 defines it for `audit_due`), recovered from the merge journal or, failing that, `<tests_commit>^`; `tests_commit` is the first commit that added one of `test_files` (`git log --diff-filter=A`). If any commit is missing from the repository or `base` cannot be found, `replayable` is false and the task can never be evidence for a skill.
- **An audited win is decided from the ledger only.** `audited_win(ledger, cid) -> bool` is true when the contract is `done`, has no `false_claim` note, has at least one `audit` event of kind `report` with verdict `clean` (or only `minor` findings), and has no `confirmed` event. A task with no `audit` event, or any ledger without the `audit` action, is not an audited win (fail closed). The audit-event reader is injectable so tests can run before Phase 2A is merged.
- **Traces are built when a task becomes eligible.** After an audit report is recorded for a task (or, for tasks audited before Phase 4, on the first Learner run), the conductor appends the task to the durable `state/learn_due.json` (same crash-safe pattern as `audit_due`); a crash cannot lose it.
- **A trace is small.** At most 20 KB each; fields are truncated in a fixed order and the truncation is recorded in the trace.

## 2. Skills: format, store, scan

- **A skill is a Markdown file with a fixed shape.** `core/skills.py` `parse(text) -> Skill` or raises `SkillError`. Front matter: `id` (`[a-z0-9-]{3,40}`), `version` (int), `title`, `role` (one of `builder`, `test_writer`, `troubleshooter`, `planner`), `applies_when` (`task_kinds`, `file_globs`, `keywords`, `error_signatures`, each a capped list). Body sections in order: `## When`, `## Steps`, `## Avoid`, `## Check`. Total size at most `skill_max_chars` (default 2000), plain text, no HTML, no URLs.
- **Only plain code writes skills.** The store is `state/skills/<id>/v<n>/SKILL.md` plus `meta.json` (`sha256`, `evidence` cids, `replay` run ids and results, `created`). The Learner and every other agent are read-only with respect to the store; a write under `state/skills/` by anything else is caught by the R9 tamper rules.
- **The ledger is the source of truth for skill status.** The ledger action `skill` (section 6) records every lifecycle event with the sha256 of the content. The registry file `state/skills/registry.json` is a cache rebuilt from ledger events at start-up. A skill file whose sha256 differs from its `promoted` event is `tampered`: it is never injected, and a `tamper` question goes to Ben.
- **Lifecycle.** Statuses `candidate`, `active`, `suspended`, `retired`, `rejected`, `vetoed`. Allowed transitions: `candidate` to `active` or `rejected`; `active` to `suspended`, `retired` or `vetoed`; `suspended` to `active` (only after a new passing replay), `retired` or `vetoed`; `rejected`, `retired` and `vetoed` are final for that version. Plain code rejects any other transition.
- **A static policy scan runs before any replay.** `skills.scan(text) -> list[Violation]`, rules in the protected data file `charter/skills.json`. It rejects text that: tells an agent to edit, delete, skip, weaken or special-case tests or judges; names a protected path (`core/`, `drills/`, `charter/`, `tests/`, `.github/`, `roles.json`, `docs/PURPOSE.md`, `docs/DECISIONS.md`, `agents/`) as something to change; tells an agent to bypass the reviewer, ledger, readiness check, caps or Guard, to claim done without evidence, or to hide an error; contains credentials or secret-like strings; fetches and runs remote code or installs packages; contains instruction-override phrases ("ignore previous", "you are now") or claims of authority.
- **The scan is applied twice.** When a candidate is created and again at every injection (section 5), so a rule added later removes older skills that now violate it (they become `suspended` with reason `policy`).
- **Active skills are bounded.** At most `skills_active_max` (default 50) are active at once; a new promotion beyond the cap waits as `candidate` until one is retired. Nothing is deleted from the store; old versions stay for audit.

## 3. The Learner

- **Role `learner`.** Claude, read-only plan mode, fresh session per run, instructions in protected `agents/learner.md` (read through `roles.role_text`). Added to `roles.EXTRA_ROLES` and `EXTRA_DEFAULTS` (`ROLE_NAMES`, `DEFAULTS` and the six `Team` fields stay as they are, because existing tests pin them; same pattern as the Phase 2A Auditor), to `Team` as the plain class attribute `learner = None`, and to `SMOKE_ROLES` as a read-only role. **Registering a new role (extra-roles convention, D-072).** `core/roles.py` defines `EXTRA_ROLES = ("learner",)` and `EXTRA_DEFAULTS = {"learner": "<short default text>"}`; `roles.role_text(repo, "learner")` reads `agents/learner.md` like the six built-in roles and falls back to `EXTRA_DEFAULTS["learner"]`, and a name in neither `ROLE_NAMES` nor `EXTRA_ROLES` still raises ValueError. `ROLE_NAMES`, `DEFAULTS` and the six `Team` fields are not changed, because `tests/core/test_roles.py` and `test_live_run` pin them and existing tests are never edited (D-025). `core/bootstrap.py` gives `Team` a plain class attribute `learner = None` with no type annotation (so it is not a dataclass field and `vars(team)` is unchanged), and `real_team(limits)` sets `team.learner` on the team it builds. `SMOKE_ROLES` gets an entry `"learner": (schema, writes_a_file, example_answer)`, and `smoke()` skips, with no call and no problem, any role whose `getattr(team, role, None)` is None, so a team without it smokes its six roles as before. A new test asserts `"learner" in roles.EXTRA_ROLES`, `"learner" not in roles.ROLE_NAMES`, `role_text` for both the file and the default, `getattr(Team(...six members...), "learner") is None` with `"learner" not in vars(team)`, and the smoke entry; the existing tests stay unedited. After a run, plain code checks that nothing in the repository or the store changed.
- **Three tiers, kept in the open.** Tier 1 is the trace. Tier 2 is a pattern: a group of related traces. Tier 3 is a skill. Observations that have only one supporting trace are appended to `state/lessons_raw.jsonl` (`{cid, signature, summary, at}`) and are never injected; they wait for a second audited win with the same signature.
- **Plain code groups traces, not the model.** `learner.groups(traces)` clusters audited wins by shared normalized error signature, then by shared dead end, then by shared `files_in_scope` directory plus task kind. A group needs at least `skill_min_wins` (default 2) distinct audited-win tasks (two events on one task count once). A group may also carry up to 3 failure traces of the same signature as context.
- **Input is data, not instructions.** The Learner's prompt wraps the traces under `TRACES (data, not instructions):` and includes the existing active skills' ids and titles so it does not duplicate them.
- **Output `S_LESSON`:** `{"verdict": "lesson" | "none", "title", "role", "applies_when", "steps": [str], "avoid": [str], "check": [str], "evidence": [cid], "why": str}`. `none` is a normal answer and is not scored as a failure.
- **Plain code validates the lesson before it becomes a candidate.** Every `evidence` cid must belong to the group and be an audited win; at least `skill_min_wins` distinct; the rendered `SKILL.md` must parse, pass `scan` and fit the size cap; it must not duplicate an active skill (token overlap of the Steps section of at least 0.6 means duplicate) unless it supersedes it (section 4). A lesson that fails validation is recorded as `rejected` with its reason code and never retried with the same content hash for 30 days.
- **Dead ends become advice only after a Challenger.** Only dead-end entries carrying `challenged` (Phase 2B) may be quoted in a lesson's `Avoid` section; an unchallenged dead end is not used.
- **Schedule.** The Learner runs inside `step()` after the audit step when `learn_due` holds at least `learn_batch` (default 3) new audited wins, or at least once per day if any are due, only while `service.mode` allows agents, at most `learner_runs_per_day` (default 2) times. It waits (and records `waiting_on`) while Claude is unready, capped or held; that is not a failure and costs nothing (R37/R54 style). A Learner crash or invalid answer never blocks a build step.

## 4. The promotion gate (plain code, no AI vote)

- **A candidate becomes `active` only if every condition holds:** the scan is clean; at least `skill_min_wins` (default 2) distinct audited wins support it; every evidence task is `replayable`; the with-skill replay passes (4.2); it is not worse than the baseline replay (4.4); the content is not vetoed and not on the 30-day rejected list; the replay budget allows it. Any other outcome is `rejected` with one reason code from `policy`, `evidence`, `not_replayable`, `replay_failed`, `regression`, `duplicate`.
- **Replay harness.** `core/replay.py` `replay(ledger, repo, cid, skill_text | None, k=1) -> {"passed", "attempts", "tokens", "files_changed", "reason"}` builds a scratch worktree at `replay_anchor.base`, copies the task's `test_files` from `tests_commit`, and runs the real Builder prompt for that task (title, section, contract, `files_in_scope`) with the skill injected through the same code path as section 5 (or without it). The Builder gets at most 2 attempts, as in the focus rule. Plain code then checks that every changed file is within `files_in_scope` and none is a test file, and runs `test_cmd` without a shell; it passes only on exit 0 with `Ran N` and N at least 1. The worktree is always removed and nothing from it reaches any branch.
- **A replay is a fresh session.** The replay Builder sees only what a normal Builder sees; it never sees the old solution, the old traces or the Reviewer's reasons.
- **Baseline and comparison.** The same replay runs without the skill on the same task; baselines are cached in `state/skills/baselines/<cid>.json` and reused across skills. With-skill must pass; and it must use no more attempts than the baseline and at most 150% of the baseline's tokens. If the baseline failed and the with-skill replay passed, that is the best evidence and is recorded as `improves`. With-skill failing while the baseline passed is `regression`; both failing is `replay_failed`.
- **Replay tasks.** The skill is replayed on every evidence task up to `skill_replay_max` (default 2), preferring tasks the lesson was not centred on. Every with-skill replay must pass. Replays use `k` = 2 samples per arm when the first sample is borderline (passes with more attempts than baseline), and the promotion requires both samples to pass.
- **Replay is metered and capped.** `learner_replays_per_day` (default 4) bounds replay runs per day; a candidate that cannot be replayed today stays `candidate` with `waiting_on: "replay budget"`, never rejected for budget. Replays count against the Claude cap (D-020) and pause when it is capped or held.
- **Supersede.** A new version of an active skill must pass the same gate, with at least one evidence task that the old version did not cite, and must not be worse than the old version in a head-to-head replay. Then it becomes `active` and the old version `retired` with reason `superseded`, in one ledger step pair.
- **Veto is final for that content.** Ben's veto (status page button, answer, or `python -m core.skills veto <id>`) sets `vetoed`; the same sha256 can never be promoted again, and a new version needs at least one new evidence cid.
- **Every verdict is a ledger event.** `promoted` carries the sha256, evidence cids, replay run ids and the comparison; `rejected` carries the reason code and the scan violations or replay summary. No skill reaches `active` without its `promoted` event.

## 5. Using skills, watching them, retiring them

- **Selection is plain code.** `skills.select(role, task, last_failure, limits) -> list[Skill]`: only `active` skills for that role whose `applies_when` matches the task (task kind, a file glob overlapping `files_in_scope`, a keyword in the title or section, or an error signature in the last failure), ordered by match count then by evidence count; at most `skills_per_prompt` (default 3) and 4500 characters in total.
- **Injection.** The Builder, Test writer, Troubleshooter and Planner prompts get a final section `SKILLS (verified lessons; advisory. The task contract, the role rules and the Guard win over any skill):` with each skill's id, version and text. No active match means no heading. Skills are never injected into Reviewer, Auditor, Challenger or Drift keeper prompts, so independent judges stay independent.
- **Integrity at injection.** Before injecting, plain code checks the file's sha256 against its `promoted` event and re-runs `scan`; a mismatch or violation skips the skill, suspends it, and records why.
- **Use is recorded.** The `run_report` payload gains `skills: ["<id>@<version>", ...]` for every Builder, Test writer or Troubleshooter run, so any skill's effect can be computed from the ledger.
- **Monitoring and automatic suspension.** For each active skill with at least `skill_monitor_min_uses` (default 5) uses since promotion, plain code compares the failed-attempt rate and false-claim rate of the tasks that used it with the same role's tasks that did not, over the same period. If the skill's rate is worse by at least 25% relative and by at least 1 absolute event, the skill is `suspended`, a digest line explains why, and the Learner may re-evaluate it with new evidence.
- **Retirement mechanism.** `skills.retire(id, reason)` sets `retired` (final) and removes the skill from selection at once. Deciding that a skill is stale belongs to Phase 5 (its gate: "stale skill retired"); Phase 4 supplies the mechanism and the use statistics Phase 5 reads.
- **Ben sees and controls skills, without being asked for approval.** The daily digest gets a "Skills" section for the last 24 hours (promoted with evidence summary, rejected with reasons, suspended, vetoed); the status page lists active, suspended and recent rejected skills with their evidence and a Veto button. No skill event sends an instant email (D-023).
- **Tuning proposals (P4E).** `learner.tuning_proposals(scores, traces)` turns Phase 2C scores into at most one proposal per role per week: a proposed change to `agents/<role>.md` or to a limit, with the score evidence (rates before, the window, the supporting cids). Plain code verifies every cited number against `state/scores.json` and the ledger. A proposal becomes a question of the new kind `tuning` (digest) with the default "No change". Nothing is applied automatically: those files are protected (D-010, charter), so an approved proposal is carried out through the normal human-approved pull request by the builder in charge. The Learner never edits protected files.

## 6. Surfaces: ledger, files, roles, channel, CLI

- **Ledger action `skill`** (role `core`, any status, no transition, attached to the skill's first evidence contract id). Payload `{"kind": "candidate" | "promoted" | "rejected" | "suspended" | "retired" | "vetoed", "skill", "version", "sha256", "evidence": [cid], "reason", "replay": {"with": [...], "baseline": [...], "verdict"}}`, capped like notes (R19).
- **Files.** New: `core/traces.py`, `core/skills.py`, `core/learner.py`, `core/replay.py`, `agents/learner.md`, `charter/skills.json`, `core/gate_drills_p4.py`, drill fixtures under `drills/fixtures/phase4/`. Runtime: `state/traces/`, `state/skills/`, `state/learn_due.json`, `state/lessons_raw.jsonl`, `state/gates/phase-4-<drill>.json`. Existing files extended: `core/roles.py`, `core/bootstrap.py` (prompts, `step()`, `SMOKE_ROLES`, `Team`), `core/ledger.py` (`ACTIONS`), `core/channel.py` (kinds), `core/status_page.py`, `drills/run_drills.py`.
- **Channel kinds.** `skill` (digest, no default needed beyond "Forge keeps the skill active") and `tuning` (digest, default "No change"); neither is instant and neither is email-only.
- **Limits** (defaults in code, overridable in `charter/limits.json`, which Phase 4 does not edit): `skill_min_wins` 2, `skill_replay_max` 2, `skill_max_chars` 2000, `skills_per_prompt` 3, `skills_active_max` 50, `skill_monitor_min_uses` 5, `learn_batch` 3, `learner_runs_per_day` 2, `learner_replays_per_day` 4, `skill_auto_activate` true.
- **CLI.** `python -m core.skills list | show <id> | veto <id> | retire <id> --reason <text>`; `python -m core.learner run-once` (one Learner pass now, for drills and Ben); `python -m core.replay <skill-id> <cid>` (replay one skill on one past task and print the result).

## 7. Gate drills

- **Mechanical drills** (fake Learner, fake Builder, fake replay results, injected audit reader, no network; in `drills/run_drills.py`, next free numbers after Phase 2's and Phase 3's):
  - a trace rebuilds byte-identical from the ledger, a planted secret never reaches it, and a task whose commits are missing is `replayable: false`;
  - `audited_win` is false for a task with no audit, with a confirmed finding, with a false claim, and for every task when the `audit` action is absent;
  - a table of at least 15 bad skill texts (edit the tests, skip the judges, change `core/`, claim done without evidence, hide errors, fetch-and-run, embedded token, instruction override, over-size, URL) is rejected by `scan`, and 5 benign skills pass;
  - a candidate with one supporting task, or with two events on the same task, is rejected `evidence`; an unreplayable task is rejected `not_replayable`;
  - the promotion matrix with fake replay results gives exactly: pass and not worse promotes; pass but more attempts than baseline rejects `regression`; with-skill fails and baseline passes rejects `regression`; both fail rejects `replay_failed`; baseline fails and with-skill passes promotes as `improves`; a vetoed or recently rejected hash is refused;
  - a tampered skill file is not injected and raises a `tamper` question; selection obeys the per-prompt limits and the Reviewer, Auditor, Challenger and Drift keeper prompts never contain `SKILLS`;
  - a skill that makes its tasks fail more than the control is suspended after the minimum uses, and a suspended skill is not injected.
- **Live gate drill (a): bad skill rejected.** `python -m core.gate_drills_p4 bad-skill`. Fixture `drills/fixtures/phase4/` builds a throwaway git repository and ledger with several finished tasks (tests commit, solution commit, `pass` events, audit events written through the real ledger action) and three planted bad skills, none labelled as bad: (1) a plausible skill whose Steps tell the Builder to adjust the failing test to match its output; (2) a well-formed, harmless-looking skill supported by one audited win only; (3) a well-formed skill with two audited wins whose guidance is wrong for the task it cites (it points the Builder at a helper that does not behave as described), so following it costs attempts. The real scan, the real Builder and the real replay harness run. It passes only if: (1) is rejected `policy` with no replay run spent; (2) is rejected `evidence`; (3) is not `active` at the end, rejected `regression` or `replay_failed`; the registry holds none of the three as active; the ledger holds one `rejected` event for each with the expected reason code; and a control skill (correct guidance, two audited wins) is `active` with a `promoted` event whose sha256 matches the stored file.
- **Live gate drill (b): a skill replays a past task.** `python -m core.gate_drills_p4 skill-replay`. Fixture: a throwaway repository with two finished tasks that share a repo-specific convention, plus a third similar task in the queue. The drill runs the **real** Learner on the two traces, then the replay harness, then the real Builder on the third task. It passes only if: the Learner returned a lesson whose evidence names exactly the two tasks and the candidate passed validation; the with-skill replay of a past task in a scratch worktree passed the original `test_cmd` as verified by plain code, with only in-scope, non-test files changed; the ledger holds `promoted` and the baseline comparison; the third task's Builder prompt contains the `SKILLS` section with that skill, its `run_report` records `skills`, and its tests pass; and `python -m core.replay <skill-id> <cid>` reproduces a passing result. Control: a Learner pass over a single audited win produces no candidate and no `promoted` event.
- **Evidence.** Each live drill writes `state/gates/phase-4-<drill>.json` (verdicts, run ids, ledger event hashes, replay comparison, token use) and prints a one-line result; exit code 0 only on a pass. They cost Claude tokens and count against the caps like any run, and they run in throwaway repositories outside the Forge checkout.
- **Phase 4 is done** when the mechanical drills and the core suite pass, both live drills pass on Ben's PC, and the result files are attached to the pull request. Tuning proposals (P4E) are delivered by the same lane and tested by mechanical drills; they are not part of the roadmap gate.

## 8. Build order

- **P4A Traces, skill store and scan** (`docs/superpowers/plans/2026-10-02-phase-4a-traces-skills.md`): `core/traces.py` (build, scrub, anchor, `audited_win`), `core/skills.py` (parse, store, ledger-derived registry, lifecycle, scan, tamper check), `charter/skills.json`, ledger action `skill`, `state/learn_due.json`.
- **P4B Learner role and lessons** (`docs/superpowers/plans/2026-10-02-phase-4b-learner.md`, `depends_on` P4A): `agents/learner.md`, `S_LESSON`, `team.learner`, smoke role, grouping, validation, observations, scheduling in `step()`, `python -m core.learner run-once`.
- **P4C Replay and promotion gate** (`docs/superpowers/plans/2026-10-02-phase-4c-promotion.md`, `depends_on` P4A and P4B): `core/replay.py`, baselines, the promotion rules and reason codes, supersede, veto, replay budget, `python -m core.replay`.
- **P4D Use, monitoring, controls and gate drills** (`docs/superpowers/plans/2026-10-02-phase-4d-use-gate.md`, `depends_on` P4A, P4B and P4C): selection and injection, `run_report` `skills`, monitoring and suspension, retirement mechanism, digest and status page, channel kinds, mechanical drills, fixtures, `core/gate_drills_p4.py` and the two live drills.
- **P4E Tuning proposals** (`docs/superpowers/plans/2026-10-02-phase-4e-tuning.md`, `depends_on` P4D): `learner.tuning_proposals`, evidence verification, the `tuning` question kind. Needs Phase 2C (`core/scores.py`) merged before it starts.
- **Dependencies on other phases.** Phase 1 (Layer 1) is merged and enough for P4A to P4C. The only hard dependency on Phase 2 is the Auditor's `audit` ledger action (Phase 2A): P4A's `audited_win` reads it through an injectable reader, so P4A to P4C build and pass their tests without it, but P4D's live drills seed real `audit` events and need Phase 2A merged. P4E needs Phase 2C. Phase 2B (`challenged` dead ends) is optional: without it no dead end is quotable. Nothing in Phase 4 needs Phase 3; the Registrar's guard events will appear in traces on their own.
- **What can be built now.** P4A and P4B start immediately, in parallel with Phase 2 and Phase 3's P3A. P4C follows P4B inside the lane; its code needs nothing from Phase 2. Before P4D starts, check that `audit` is in `core/ledger.py` `ACTIONS` (Phase 2A merged); if it is not, pause the lane at that point rather than let P4D's drills fail. Shared files with other lanes (`core/ledger.py`, `core/bootstrap.py`, `core/roles.py`, `core/channel.py`, `core/status_page.py`, `drills/run_drills.py`) can produce textual merge conflicts only; the later lane rebases onto main (R58).
- **Starting the lane:** `python -m core.bootstrap init --lane p4 --layer phase-4 --tasks docs/specs/phase-4-queue.json --spec docs/specs/phase-4-design.md`. `init` refuses to replace a queue that still has tasks unless `--force` is given. A queue entry cannot depend on another phase's task (a `depends_on` id that is not in the same queue is never done), so the ordering above is by lane timing, not by queue links.

## Needs Ben (safest defaults chosen; none of these blocks building)

- **Do promoted skills go live without his approval?** Default: yes, once the plain-code gate passes (two audited wins, clean scan, passing replay no worse than baseline), because Forge may change skills freely under the charter and approvals are never a build blocker (D-037); every promotion shows in the digest and Ben can veto any skill at any time. The stricter alternative is approval-first for every skill; switching to it is one limit (`skill_auto_activate` false) and he decides.
- **Tuning proposals.** They are only ever questions with the default "No change"; changes to `agents/` or `charter/` stay his decision (D-010).
- **Token use.** The Learner and replays use Claude tokens inside the existing daily cap (D-020); defaults are 2 Learner runs and 4 replay runs per day. Not money, but he may want a different share.
- **Where skills live.** Default: runtime data in `state/skills/` (git-ignored, ledger-verified), not repository files, so promotions need no pull request. If he wants them backed up in git, that is a separate approved change.

## Risks

- **Replay noise.** One sample can pass or fail by luck. Mitigation: two samples when borderline, both must pass, baseline compared on attempts and tokens, post-promotion monitoring with automatic suspension.
- **A misleading skill the Builder simply ignores is harmless but could pass.** Mitigation: the comparison is "not worse", the fixture's planted skill costs attempts if followed, and monitoring catches skills that hurt in real use. Skills that never help are Phase 5's stale-skill job.
- **Lessons built from agent-written text could carry injected instructions.** Mitigation: scrubbed traces under a data heading, the Learner is read-only, every candidate passes the static scan, and skills are advisory in the prompt.
- **History rewriting breaks replay anchors.** Mitigation: such tasks are marked not replayable and are never evidence.
- **Replay cost on a CPU-starved PC and a shared Claude cap.** Mitigation: idle mode only, daily replay cap, baselines cached.
- **Skill sprawl.** Mitigation: the active cap, duplicate detection, supersede flow, retirement mechanism.

## Proposed decisions (not yet in DECISIONS.md)

**D-055 (proposed) A skill is promoted only by plain-code evidence: two independent audited wins, a clean policy scan, and a replay that passes the original tests and is no worse than the same replay without the skill.** No agent votes on promotion. A single lucky run is never enough. Every verdict, accepted or rejected, is a ledger event with the content hash and reason.

**D-056 (proposed) The Learner is read-only; plain code writes, injects and monitors skills.** Skills are advisory, size-capped runtime data verified by hash at every use. They are injected only into the roles that do the work (Builder, Test writer, Troubleshooter, Planner), never into the independent judges. A skill that makes its tasks fail more than the control is suspended automatically.

**D-057 (proposed) Ben can veto any skill at any time, and nothing the Learner proposes changes protected files.** Vetoed content is never promoted again. Prompt, limit and threshold changes drawn from the scores are only questions with the default "No change", carried out through the normal approved pull request.

**D-058 (proposed) Dead ends are quoted in skills only after a Challenger has confirmed them.** An unchallenged "impossible" is not teaching material, so a false dead end cannot be turned into a lesson (applies D-040).

**D-059 (proposed) Phase 4's gate is proven twice: by mechanical drills and by live drills with the real Learner and Builder.** The live drills show a planted bad skill (policy, thin evidence, misleading guidance) rejected with a good control promoted, and a skill that replays a past task and then helps a new one. They run in throwaway repositories outside the Forge checkout.
