# Layer 1C: planning and drift

> Plan task P1C. Serves `docs/specs/layer-1-design.md` §2 (Manager and Drift keeper roles), §3.2 (focus rule) and §3.7 (drift keeper after every merge), implementing D-026. Builds on `core/bootstrap.py` (R1–R40), `core/finalize.py` (the merge journal marks drift) and `core/ledger.py` (completion from the event log). Gate (§7): coverage must rise; re-plan triggers; a fresh Manager sees the ledger only.

## Decisions this plan makes

- **Requirements are numbered spec items.** `core/coverage.py` splits the spec (`limits["spec_file"]`, default `docs/specs/layer-1-design.md` in the layer worktree) into requirements: every top-level list item or table body row inside a `## N. Title` section gets id `N.k` (k counts from 1 in document order); a section with no items is one requirement `N`. So §3.7 is "Drift keeper runs after every merge". Code blocks are ignored.
- **Tasks name what they cover.** A task carries `covers: ["3.7", ...]`. Manager tasks must have it; planner tasks may (kept if valid).
- **Coverage is verified, never trusted from the queue.** A task counts as done for coverage only when the queue says `done` **and** the ledger's event log holds a `pass` for its contract (hash chain verified). A requirement is `unclaimed`, `open`, `partial` or `covered`; it is `covered` only when **every** task claiming it is verified done. The coverage score is the sum over requirements of (verified claimants / claimants), an exact fraction, so a requirement split over four tasks rises by a quarter per merge without being marked covered early.
- **A merge's gain is measured against the same task set.** For a merged task T: gain = score(counted ∪ {T}) > score(counted), both computed on the current queue and ledger. `counted` is adopted on first use from all work already done (every drift mark and every verified done task; if `drift_due` is set at adoption, the newest mark stays uncounted). Historical work is therefore never credited to a new merge.
- **Active time, not wall time.** `state/activity.json` accumulates the seconds spent inside agent runs of team roles and the Manager (measured with the conductor clock, excluding readiness probes), test runs, judge commands and mutation runs. Pauses, cap waits, idle sleeps and restarts add nothing.
- **Builder focus time (D-026, 20 minutes).** Each task keeps `focus_s`: builder run seconds since its tests were accepted or since its last troubleshoot. The builder is launched with `timeout_s = limit - focus_s` (agents that accept it kill the process tree at that deadline); a run whose measured time reaches the remaining budget fails with `focus limit` and hands off to the Troubleshooter at once, and with troubleshooter rounds used up it blocks. Limit: `limits["builder_focus_s"]`, default 1200.
- **Stall rules bring in the Drift keeper.** Every step, before any threshold is checked, newly marked merges are recorded (restart-safe, each merge once), which resets the active window. Then: 3 merges in a row without gain (`limits["drift_no_gain_merges"]`, default 3), or 2 active hours with no merge while build work remains (`limits["drift_no_merge_active_s"]`, default 7200), set a durable `stall`. The Drift keeper runs whenever `drift_due` or `stall` is set, with the coverage map and the stall facts. A stall forces a re-plan whatever the keeper answers; its reasons are kept.
- **The Manager re-plans from the ledger and spec only.** A re-plan is stored durably (`replan` with an id) before `drift_due` or `stall` is cleared. The Manager (Claude, read-only, `permission_mode="plan"`) runs in a throwaway worktree at the layer tip. Its prompt holds exactly: its standing rules, the spec text, the requirement coverage map, the ledger's contracts (id, title, spec_ref, status, attempts, completed) and the re-plan reasons. Never notes, trouble notes, review feedback, run records, questions, emails or dead ends. Its role text lives in `core/manager.py` (`core/roles.py` has a fixed role list pinned by its tests).
- **Proposals are validated completely, twice.** Full schema and types; only known keys; unique ids that clash with no queued task or ledger contract; non-empty title and section; `covers` non-empty and all known requirement ids; `files_in_scope` relative, no `..`, nothing under `tests/`; `test_files` under `tests/core/`, named `test*.py`; `test_cmd` exactly `python -m unittest <all its test files>`; optional `needs`. A read-only Manager that changed files is rejected. The Reviewer then checks the plan. At acceptance the tasks are validated again against the current queue (plus `bootstrap.validate_task`), appended in one durable queue write that also records the re-plan id, and only then is the pending re-plan cleared, so a crash never loses or duplicates it.
- **Bounded.** 2 rejected proposals, a missing spec, or 2 accepted re-plans with no coverage gain since: PAUSED and a `replan` question to Ben, as before. With no Manager configured (older harnesses), a re-plan pauses and asks Ben exactly as today.
- **The gate stays closed** while a stall or re-plan is pending.

## Acceptance

- `python -m unittest discover -s tests/core` passes, with every existing test unchanged.
- `python drills/run_drills.py` passes, drills 1–13.
- Each rejected-plan gap is pinned by a test: merge recorded before the active-time check (boundary); tests outside `tests/core` and wrong types rejected, also at acceptance; partial coverage stays partial; baseline adopts completed work; pauses and cap waits add no focus or active time and a running attempt is cut at the focus deadline; crash between drift writes neither double-counts nor loses a re-plan; coverage requires a ledger pass.
